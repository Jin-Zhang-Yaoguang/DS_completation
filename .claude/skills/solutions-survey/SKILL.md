# 目标

针对指定的 Kaggle 比赛，用 Kaggle API 搜索公开高分 notebook、精读源码，
维护一份**持续更新的方法论综述**：`<比赛目录>/competition_description/public_solutions_survey.md`。

**综述只写调研结论本身，不与本项目现状做对比**；对比与行动项由主对话另行整理（如写入 `model/experiments.md`）。

# 两种模式（自动判断）

- **首次全量**：目标比赛还没有 survey 文档 → 走完整调研流程，产出全新综述。
- **每日巡视（默认）**：survey 文档已存在 → 增量模式：只精读**新出现**的方案，
  增量更新综述，并向用户汇报「今日发现」。用户日常说「巡视」「看看有没有新方案」即此模式。

# 输入

- **比赛 slug**（如 `playground-series-s6e7`）。若用户只给了比赛文件夹名，从该文件夹
  `competition_description/overview.md` 中的来源链接里解析 slug；若项目里只有一个比赛文件夹，直接用它。
- **Kaggle API token**：按顺序尝试 `~/.kaggle/kaggle.json`、环境变量 `KAGGLE_KEY`；
  都没有则询问用户。禁止把 token 写入任何产出文件。

# 通用步骤

## 1. 列出候选 notebook

用**三种排序**各取 top 20，合并去重：

```python
# GET https://www.kaggle.com/api/v1/kernels/list?competition=<slug>&sortBy=<sort>&pageSize=20
# sort 依次取 scoreDescending、voteCount、dateCreated 三轮
# 请求头: {"Authorization": f"Bearer {TOKEN}", "User-Agent": "kaggle-api"}
# 关注字段: ref(作者/slug), title, totalVotes（bestPublicScore 经常为空，分数以标题自报为准）
```

**dateCreated 排序不可省略**——分数榜和票数榜都发现不了「新发布但尚未热起来」的方案
（实测：某作者的表格 NN 系列 0 票，只有按时间排序能看到），而这类方案恰是每日巡视的主要猎物。

## 2. 确定精读对象

**首次全量**：筛 6~10 份。
**每日巡视**：读取 survey 文档附录的「已调研清单」，与候选列表 diff——
只精读：① 新出现的 ref；② 标题分数显著刷新的旧 ref（说明方案大改版）。
巡视日若无新方案，直接汇报「今日无新方案」，仅在更新日志记一行，结束。

筛选标准（两种模式通用）：
- **优先**：标题含 CV/LB 分数的原创方案（单模、特征工程、融合架构）、高票 EDA、消融实验类；
- **排除**：纯「提交融合器」（收集他人 submission 做投票/hill climbing，无原创模型）——
  在已调研清单中标记为 `skip`，避免每天重复判断；
- 兼顾多样性：GBDT 单模、神经网络、融合方案、教学解读各留代表。

## 3. 批量拉取源码

```python
# GET https://www.kaggle.com/api/v1/kernels/pull?user_name=<user>&kernel_slug=<slug>
# 返回 JSON: blob.source 为 notebook JSON（或纯脚本文本）
# notebook JSON 按 cells 展开为 "# ===== cell i [type] =====" 分隔的文本
# 存入 scratchpad 临时目录（勿污染项目目录），每份一个文件
```

## 4. 逐份精读，提取五要素

1. **特征解读**：对数据/字段/生成机制的洞察（EDA 结论）；
2. **特征工程**：编码方式（目标编码/分箱/交互/统计特征）、缺失处理、是否防泄漏；
3. **模型**：数量、类型、关键参数与「操作点」（深浅/学习率/正则强度/早停配置）；
4. **指标对齐技巧**：类别不平衡处理（训练权重 vs 决策校正）、早停指标选择；
5. **融合方式**：成员构成、权重搜索方法、算术/几何平均、是否共享冻结 CV；
6. 附：其自报的 CV / LB 分数。

特别注意**消融实验类 notebook**——其证伪结论（哪些方法无效）与正向结论同等重要。

## 5. 更新综述文档

文档固定结构（增量更新时保持骨架，只动需要动的部分）：

```markdown
# 公开高分方案调研 — <比赛名>

> 首次调研时间、方法、目的（一段）

## 更新日志          （每次运行一行：日期 | 新增/复核了什么 | 一句话结论）
## 一、公开榜格局     （分数段 × 方案类型表格；有变化才更新）
## 二、逐个方案分析   （每份：作者/标题/分数 + 五要素；新方案追加，标注调研日期；信息量大的标 ⭐）
## 三、社区共识配方   （交叉验证过的结论 + 避坑清单；新证据出现时修订，标注修订原因）
## 附录：已调研清单   （表格：ref | 标题分数 | 状态 read/skip | 调研日期——巡视模式的 diff 基线）
```

要求：结论精确到数字（分数、参数值）；标注出处方案；只写调研所得，不写与本项目的对比或行动建议。

## 6. 向用户汇报

**巡视模式的汇报格式**（重要，用户每天看的就是这个）：
- 今日新增方案数与清单（无新方案就一句话）；
- 每份新方案的**一句话方法概括 + 分数**；
- **是否有值得行动的新信息**：新技巧？共识被修订？榜局变化（如出现新的分数天花板）？
  ——明确说「有/没有」，有则给出具体是什么。

# 注意事项

- Kaggle notebook 页面是 JS 渲染的，**必须走 API**，不要用 WebFetch 抓网页；
- 尊重社区规范：综述用于学习方法论，注明出处；不下载、不搬运他人 submission 文件；
- 巡视模式控制成本：diff 后通常只精读 0~3 份，不要每天重拉已读过的源码；
- 已调研清单是幂等运行的关键——每次更新文档时务必同步维护；
- **清单必须逐条枚举每个见过的 ref，严禁「其余低票类 skip」式模糊通配行**——
  通配无法机器 diff，下次巡视会把老候选全部误报为新增（实测教训）。
  首次全量调研时，未入选精读的候选也要逐条登记为 skip 并附一句原因。
