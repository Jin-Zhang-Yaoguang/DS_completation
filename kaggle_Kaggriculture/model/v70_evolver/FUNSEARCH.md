# FunSearch 式双层进化方案(v71)

一句话:**外层"提议者"(大模型)读诊断 → 改 `scheduler.py` 一处 → 内层"筛选器"(GA + 配对 holdout 验收)决定收不收**。按固定节拍轮转,用户只给总代数预算。

## 1. 实证依据(2026-09-13,diag/)

| 实验 | 结果 | 含义 |
|---|---|---|
| 冠军 cfg × 4 组不同 8-seed(`champ_noise.py`) | 均值 -65.0k,**组间 sd 7.2k,极差 17k** | 8-seed 验证尺的噪声 ≫ 候选间差距(1-2k) |
| 冠军 vs 种群 top2,32 个新 seed 配对(`paired_noise.py`) | 配对差 per-seed sd 8.5k-12k;**8-seed 均值 se≈3-4.4k,32-seed se≈1.5-2.2k**;胜局各 16/32 | structv3 的登基判定(8 seed 硬比较)信噪比 <1 |

结论:structv3"gen70 冠军 730 代未被超越"**不可靠**——gen772 候选(valid -65,163 vs -63,881)在噪声内,等价于掷骰子。本方案第一件事是把尺子做准。

## 2. 节拍(用户只定总代数 N)

- **seed 轮换:10 代/期**(不变,防过拟合机制已验证有效)。
- **一刀 = 最多 80 代(8 期)**;早停:连续 40 代(4 期)无登基 → 提前结束这一刀。依据:structv2 阶跃集中在前 60 代,structv3 gen70 后无效。
- **刀间开销 <1 min**:冒烟 8 局 + 验收 64 seed×6 对手×2 cfg=768 局(≈20 s)+ 诊断脚本。提议者(大模型)写 patch 的时间不占算力。
- **时间换算:35 s/代,100 代 ≈ 58 min;N 代 ≈ N/60 刀**(早停时刀数更多)。例:通宵 8 h ≈ 820 代 ≈ 10-15 刀。
- **用户接口**:`python funsearch.py --budget-gens N` 后台跑,driver 自动按节拍切刀;每刀结束写 `runs/_signal/NEED_PATCH.json`(含诊断包)。用户用 `/loop 25m 继续 funsearch` 定期唤醒提议者:有信号 → 提议+启动下一刀;无信号 → 只推看板。预算耗尽 driver 自停并写收官报告。

## 3. 提议者(外层,大模型)

每刀开始读**诊断包**,输出一个 patch:

1. **诊断包内容**
   - 上刀冠军 cfg 与 SPACE 边界的贴合度(参数顶到边界 = 空间不够,先扩边界而非改结构)
   - 种群各维收敛度(末代 32 个体每维 sd/range:收敛 = 榨干;震荡 = 该维不敏感)
   - **动作审计**(`diag/action_audit.py`,待写):冠军 vs 榜首带各 5 局——每步人次、各动作计数(WATER/PLANT/HARVEST/FERTILIZE/…)、工人空闲率、按天资产曲线;输出差距最大的三项
   - 上刀验收结果与拒绝原因(若被拒)
2. **提议规则**
   - 单变量:一刀只改一个机制,否则无法归因
   - 新旋钮进 SPACE;**patch 必须能退化为旧行为**(新开关默认 0/旧值),便于 GA 自己决定用不用
   - 必须过冒烟:冠军 cfg 在新骨架 8 局分数 ≥ 旧骨架 × 0.85,否则视为 patch 有 bug,重写
3. **候选刀库**(初始优先级,每刀由诊断重排)
   - K1 收割流水线/动作密度(6.6 → 目标 9+ 人次/步;WATER 41 vs 108)
   - K2 施肥流(榜首 feel the agi d14+ 每日 10-20 次、全程 162;我方 ~75)
   - K3 雇工节奏曲线(早期雇工时序)
   - K4 卖货时机市场响应(`sell_timing` 0/1 → 连续阈值)
   - K5 三天阶段轮作表(SpaTaro:麦→畜→瓜→莓→清仓)
   - K6 清仓策略 d27-29
4. **拒绝处理**:同一方向最多重试 1 次(换实现),再拒则降级到下一候选;被拒的 patch 存 `runs/k{N}/rejected/` 留档。

## 4. 筛选器(内层,GA)

- GA 本体不变:pop 32 / elite 4 / 均匀交叉 / 30% 高斯变异;**热启动**自上刀冠军 + 31 变异体。
- **登基判定升级**:验证 seed **8 → 32**(固定);触发条件不变(训练分创新高);判定改为**配对**:候选 vs 现冠军在 32 valid seed 上的配对差均值 > 0 且 t ≥ 1.5(se≈1.5-2k)。
- **修 6% 浪费**:验证失败的 cfg 记指纹,同一 cfg 不重复复测。
- **刀级验收**:新刀冠军 vs 旧刀冠军,**64 个 holdout seed**(固定、与 train/valid 不重叠、跨刀不变)配对,接受条件:均值差 > 0 且 t ≥ 2。接受 → 成为下一刀基线;拒绝 → 回滚骨架(每刀 `scheduler_k{N}.py` 快照)。
- 所有刀共用同一把 valid/holdout 尺 → 全程可横比;看板 run 名 = 刀名,竖虚线分刀。

## 5. 刀 0(开工前准备,不占代数,预计 3-4 h)

1. `evolve.py`:valid 8→32、配对登基、指纹去重、holdout 集固定(`holdout_seeds.json`)
2. `funsearch.py` driver:预算/节拍/早停/信号文件/快照回滚/收官报告
3. `diag/action_audit.py`:动作密度审计;`diag/smoke.py`:冒烟
4. **重测 structv3 基线**:gen70 冠军 + 末代种群 top4 在 64 holdout 上配对 → 选出真正的刀 0 基线(可能不是 gen70)
5. 第一刀 patch:K1 收割流水线

## 6. 记录

- `runs/k{N}_{name}/`:state/history/best_cfg + `proposal.md`(提议依据、patch 摘要)+ `verdict.json`(验收数字)
- `experiments.md` 每刀一条;看板逐代推送 + 每刀一条小结(替代每 10 代)
- 全程本地进化,不涉及提交;上线仍须用户放行

## 7. 风险与对策

- patch 有 bug → 冒烟拦截 + 快照回滚
- 提议者间接过拟合 holdout → 提议者只看 train/valid 期诊断,**不看 holdout 逐局结果**,只看验收结论
- 8 worker 算力:每刀 ≤ 47 min,刀间 <1 min;不并行多刀(避免 CPU 争抢改变 35 s/代基线)
