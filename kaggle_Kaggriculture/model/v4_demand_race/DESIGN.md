## 0. TL;DR

这个游戏不是"把农场种好"的单人优化题，而是**对一个共享的、有限的、可完全观测的
城镇需求池的抢占赛**。公开 meta（replay tape 复刻）把单人生产效率做到了接近上限，
但在三个维度上留着结构性空当：**① 对手状态其实可以被几乎完全重建，却没人用；
② 商店抽签决定了本局哪些产品"有坑"，而 84% 的榜上 agent 完全不适应；
③ 评级只看胜负，Pr[win]=Φ(μ/σ) 的含义——落后加方差、领先降方差——没有任何
公开 agent 实现过。**

V4 的答案：**离线搜索出来的参数化生产计划**（不是抄的 tape，而是自己搜的任务图）
+ **在线三个账本**（需求坑账本、对手账本、胜率账本）驱动的市场执行层。
生产层保持确定性与连贯性（社区反复验证"稳定生产 + 只调市场"是唯一持续有效的
迭代方式 [survey §2.1]），全部对抗性智能集中在市场层。

## 1. 第一性原理：游戏的真实结构

720 回合、双人、终局银行定胜负。拆成三个耦合度递减的子问题：

### 1.1 生产调度（≈单人问题，离线可解）

早期市场深度 I0=10,000，双方开局动作对彼此价格影响极小，因此**前 ~10 天的最优
生产计划几乎与对手无关**。这解释了为什么固定 tape 能统治榜单：它就是这个单人
子问题的一个高质量解。约束是动作预算：每单位每回合 1 个动作，720 回合 × 约 11
个单位 ≈ 8,000 个动作预算，而移动、浇水、喂食都要花预算。

### 1.2 需求坑争夺（真正的博弈面）

城镇是唯一的外生需求。机制精确可算 `[engine]`：
- 每家商店实例每 4 步（每天 6 次）买其菜单上每种商品 1 个（单品店 ×2）；
- 城镇中心每 24 步买每种非肥料商品各 1 个；
- 商店在 day 2,5,8,…,23 各解锁一家（有放回抽样，共 8 家）。

由此，每种产品整季的**需求坑**（期望值）与卖进坑里 vs 平铺倾倒的收入差
[survey §3.2]：

| 产品 | 整季坑（期望） | 卖进坑 | 平铺倾倒 | 收坑的商店数 |
| --- | ---: | ---: | ---: | ---: |
| STRAWBERRY | 426 | $100,445 | $4,173 | 4 |
| MILK | 327 | $86,662 | $6,432 | 3 |
| WOOL | 228 | $54,340 | $8,097 | **1**（34% 赛季无买家） |
| WHEAT | 525 | $21,152 | $10,813 | 5 |
| MELON | 30 | $8,184 | $7,416 | **0**（但 sq 曲线极耐倾倒） |

**坑是共享的、先到先得的**。双方同回合卖单按 list index 逐单位交错结算
`[engine _process_market]`，所以争夺的分辨率是"回合"：早一回合下单就整批先手。
公开实测"抢先一回合卖 premium"这一个技巧就值 +1.7k~+3.2k margin [survey §2.1 c15/c18]。
全局收入上限约 $703k/局（双方合计），公开最好的对局只拿到 48% [survey §3.2]——
瓶颈从来不是市场的支付意愿，是**吃坑的执行与时序**。

### 1.3 组合适应（对随机性的响应）

本局哪些产品有坑由商店抽签决定，这是游戏里唯一的重大外生随机。极端例子：羊毛
只有 YARN_STORE 收，而有放回抽样下 **34% 的赛季一家也不出**——羊群价值 $39k
vs $11k，差 3.5 倍 [survey §3.2]。适应窗口是 day 2/5/8 的解锁时刻。榜上绝大多数
tape 对此完全不响应（wool 商店 day 9 出还是 day 24 出，种植组合零变化 [survey §1.2]）。

### 1.4 三个子问题的正确分工

| 子问题 | 时机 | 方法 |
| --- | --- | --- |
| 生产调度 | 离线（提交前） | 参数化计划 + 大规模本地搜索 |
| 需求坑争夺 | 在线（每回合） | 账本驱动的市场层 |
| 组合适应 | 在线（day 2–9 少量决策点） | 商店信号 → 预留产能的激活 |

## 2. 十条硬约束（每条都有来源，违反任何一条的设计直接否决）

1. **评级只看 W/L/T**。优化目标是 Pr[win]=Φ(μ/σ)，不是 E[margin]。落后时加方差
   是对的，领先时降方差是对的 [survey §3.3]。
2. **动作只执行到 step 718**，index 719 是死的 `[engine]`。
3. **不读 `obs["step"]`**，用 `day*24+hour`（seat-1 序列化缺字段）[survey §3.1]。
4. 市场列表 **SELL 必须排在 BUY 前**（同回合卖出所得才能供资购买）`[engine]`。
5. **日终自动入库**：`_drop_inventories_to_shed` 会把所有随身物品自动放进 shed
   `[engine L878]`。人肉跑回 shed DROP **只在当天就要卖/要用时才必要**——这是
   V1 移动占比 2/3 的最大单一浪费源。
6. **一次性作物熟了不收会烂**：到 `max_lifespan_step` 后每 2 步 -1 yield 直到变
   杂草 `[engine L759]`。收获截止是硬约束，不是偏好。
7. **端到端 RL/BC 不做**：社区多组独立实验天花板 80k，规则方案 140k–190k
   [survey §3.4]。搜索用在离线，在线只跑规则（0.5ms 级）。
8. **第四象限不买**：多方实测负 ROI [survey §3.2]。
9. **一次只改一个机制**，双席位配对评测，输给母体一票否决 [survey §2.1 协议]。
10. **本地对照要钉商店序列**：杂草与商店共用 RNG 流，改动只要动了地块占用数就
    重掷城镇（实测少雇一个 hand → 0/16 seed 同城镇）[survey §3.3]。

## 4. 模块详设

### 4.1 OpponentLedger —— 本方案的信息学核心

**关键事实：对手几乎是完全可观测的，只是没人去算。** 公开的观测里：

- 对手**整张农场** tiles 可见 `[engine]`：每株作物的 `crop / planted_day /
  yield_units`、每头动物的 `animal / placed_day / fed_today`、每个结构。
  → **对手未来每一天会收获什么、收多少，是可以精确预报的**（作物成熟表是确定函数）。
- 对手**金币**可见。
- 市场 inventory 可见，而城镇 drain 是确定性的（商店列表可见、tick 规则固定）
  → 逐回合反解出**对手每种产品卖了多少**：
  `opp_net[item][t] = inv[t] − inv[t−1] + drain[t] − my_net[item][t]`
- 对手不可见的只有 shed/seeds/随身。但：
  `opp_carry[item] = Σ(其收获事件, 从 tiles 的 yield 归零推断) − Σ(其已卖, 上式)`
  → **对手的在途库存被重建出来**（误差源仅剩 shed 溢出与其 BUY_PRODUCT，都很小）。

三个直接应用：

1. **卖出预报**：对手 melon 的 `planted_day` 全可见 → 它 day 10–12 必然收获、
   随后必然抛售 → 我方 melon 在其成熟前 1–2 天出手，抢占 sq 曲线的高位。
2. **战略预警**：对手 day 5 起建 6 个 pasture → milk war 将至 → Router 把预留
   产能从牛转向羊/草莓（错峰而不是对撞；镜像对撞的结局是双方银行一起塌到 40k
   [survey §2.1 bug 表]）。
3. **终局估值**：`μ_opp = opp_money + Σ opp_carry[item] × 预期实现价 + 其在场
   资产的剩余产出`。这是 WinLedger 的输入。

公开方案里最接近的是 raykkretzschmar C68 的"对手抢跑 horizon 推断"（只用了市场
反解这一半，fit 一个 1–6 的整数）[survey §2.1]。没有任何公开方案用 tiles 做收获
预报。**这是我们相对整个公开生态的差异化 alpha。**

### 4.2 HoleLedger 与卖出时序

每回合维护，纯算术：

```
scarcity[item]      = I0 − inv[item]                    # >0 在稀缺分支
remaining_drain     = f(当前商店列表, 剩余 step, 未来解锁期望)   # 确定 + 期望两段
hole_left[item]     = remaining_drain − 预计流入(我方在途 + opp_carry + 双方在场产能)
```

卖出规则（替换 V1 的固定价格地板）：

- `hole_left > 0`：坑够大，可以等——但**等的上限是对手的下一次收获预报**
  （OpponentLedger 给出）。在对手供给到来前一回合出手（race-to-the-hole）。
- `hole_left ≤ 0`：坑会被填满，转入先到先得模式——立刻分批卖，每回合一批，
  批量按"当前价 − 批末价"的自压损失 < 阈值来定（价格函数本地精确可算）。
- 肥料永远即收即卖（town drain=0，只有 glut 分支，只跌不涨 [survey §3.2]）。
- WHEAT 反向操作：它的坑最大（525）但单价低，**早期是买入品**（囤饲料，
  day 21 价格近翻倍 [survey §3.5-18]），晚期把余粮卖进坑。

### 4.3 WinLedger 与终局模式（无人做过的部分）

```
μ_me  = money + shed 液值(按坑内/坑外分段定价) + 在场资产剩余可实现产出
μ_opp = 同式（用 OpponentLedger 的重建值）
Δ     = μ_me − μ_opp
```

模式切换（day 20 起生效，之前恒为 NORMAL）：

| 条件 | 模式 | 行为 |
| --- | --- | --- |
| Δ > +5k | LOCK | 尽早清算、只吃确定的坑、不再投资，降方差 |
| −5k ≤ Δ ≤ +5k | NORMAL | 按 HoleLedger 正常时序 |
| Δ < −5k | GAMBLE | 集中持有 1–2 种 premium 延后卖（赌对手先砸盘/hinge 尖峰），加方差 |

±5k 阈值取自镜像局 margin 的实测中位数（4.5k–6.8k [survey §3.2]），即"噪声带宽"。
理论依据：胜率 = Φ(μ/σ)，μ 落后时提高 σ 是唯一正确方向 [survey §2.10 wins-not-money]。
这个模块的预期收益不在平均金币（可能为负！），而在**把"注定小负"的局翻成
五五开**——正是评级唯一在乎的东西。

### 4.4 Router：商店信号 → 预留产能激活

核心矛盾：羊 day 0–1 就要买（first_yield 6 天 + 回本窗口），而第一家商店 day 2
末才揭晓。解法是 **latent capacity**（借鉴 indarkarhana 的 latent pasture
[survey §2.6]，但做成系统机制）：

- **Day 0 固定开局**（无信号先验，离线搜出，当前假设：2 SHEEP + 2 COW + wheat
  引导 + melon 播种。羊先买 2 只是对 34% 无 yarn 赛季的对冲仓位）。
- **预留产能**：在 shed 旁多建 2–4 个已在服务路径上的空 pasture（建造免费
  `[engine]`，占地但不占钱）。
- **决策点 day 2/5/8**（每家新店解锁后的次日清晨）：
  - 见 YARN_STORE → 激活：买 2 羊入预留栏（每家 yarn store 每天吃 12 wool，
    双倍 drain）；
  - 见第 2 家奶类商店（PIZZA/ICE_CREAM/SMOOTHIE）→ 加牛；
  - 见第 2 家草莓商店（4 家收它，最容易凑）→ 启动草莓-肥料引擎（见 §5）；
  - day 8 仍无 yarn → 永久放弃加羊，预留栏转牛或挖掉种 melon。
- 决策是**激活/放弃预留**，不是重规划——路线几何、卖单结构不变，保持 §3 信条。

### 4.5 Executor：V1 调度器的三处结构升级

1. **删掉"人肉运货回 shed"**（V1 最大浪费）：利用日终自动入库 `[engine]`，
   只有"当天要 SELL/要喂"的货才专程运送。预计把移动占比从 ~66% 压向社区的
   55% 基准，长期目标 40%。
2. **全局指派替代逐单位贪心**：每回合把待办任务 × 空闲单位做一次最小成本匹配
   （≤11 单位 × ≤30 任务，匈牙利算法微秒级），消除两个单位奔向同一目标的抢占。
3. **收获截止硬约束**：一次性作物的烂窗 `[engine L759]` 进任务优先级 0 层
   （与"动物明天逃走"、"作物今晚枯死"同级）。

### 4.6 PlanSearcher：离线搜索

- **参数空间**（~30 维）：herd 组成与上限、各作物地块数、预留栏数、买地日、
  雇佣时刻表、卖出批量/阈值、Router 各触发条件、终局起始步。
- **算法**：CEM（交叉熵）起步，够用；不追求花哨。
- **fitness 必须是对抗性的**：solo 金币会系统性高估 premium 投资（坑被对手吃
  一半就不值了）。评估集 = ⅓ 镜像自身 + ⅓ 公开 meta 代表（v1_adaptive_market
  正好是现成的 8C/4S meta 执行体）+ ⅓ 天梯分档参考，双席位、钉商店序列。
- **算力预算（2026-09-01 修订：C++ 引擎已就位）**：仓库内已有 1.32.7 bit-exact
  C++ 模拟器 `kagsim`（见 §10 资产清单），实测本机 idle 局 **50,331 局/s**（全核
  `run_many`）、带 Python agent 回调的 live 双席位局 **0.26–0.32 s/局**（瓶颈已是
  agent 的 Python 代码本身）。据此 CEM 的规模上调：每代 60 个体 × 24 局（钉住的
  商店场景 × 双席位）≈ 8 分钟/代（8 进程并行则 ~1 分钟/代），一夜可跑 300+ 代
  或多轮不同随机重启。评估作业按个体切分给多个 subagent / 进程并行执行——
  个体之间零依赖，线性加速。

## 5. 肥料-草莓引擎（被公开分析系统性低估的复利回路）

引擎事实链 `[engine L799-800]`：ongoing 作物在产出日若"当天浇过水且在施肥期内"
则 +2 而非 +1；`yield_units` 的 cap 是 `min(max_yield, current+bonus)`——**及时收获
（收后归零）则每个产出日 +2 永不撞 cap**。草莓一生 4 个产出日：

```
不施肥：4 × 1 = 4 单位/株（公开分析普遍按这个算）
施肥+勤收：4 × 2 = 8 单位/株 —— 产量翻倍
```

成本侧：肥料来自动物的免费日产（每头存活动物每天 1 个，无论是否喂食
`[engine _daily_refresh_animals]`），机会成本仅为其 glut 卖价 ~$98；FERTILIZE
一次覆盖 3 天，每株草莓一生约需 4–5 个肥料。收益侧：草莓坑内实现价 $200+，
每株增产 4 单位 ≈ +$800，肥料成本 ~$450，再扣动作成本仍显著为正；且它消化了
本来只能贱卖的肥料流。**畜群（产肥）→ 草莓（吃肥翻倍）→ 全场最大的坑（$100k）**
构成一条复利回路，这是 V4 中期（day 8–24）的主产线，也解释了顶级 tape 为什么
收敛到 40+ 株草莓配畜群 [survey §2.1 c16]。
（V1 因移动预算养不起草莓每日浇水而整个放弃了它；§4.5-1 的动作节省正是为这里腾预算。）

## 6. 评测协议（M0，先于一切功能开发）

1. **对手池**：`pass/random/starter`（冒烟）+ raykkretzschmar 参考天梯 tier0–9 +
   `v1_adaptive_market`（meta 代表）+ 我方历代（母体一票否决）。
2. **本地 harness**：双席位配对（同 seed 两席位 margin 相加）；商店序列钉住——
   **直接复用 `model/v116_heuristic_gold_search/replay_arena/` 的 `kagsim_scenario`
   扩展**（`Game.force_shops(list)`，agent 只见当前已解锁前缀，无未来泄漏），
   不再需要 patch 官方引擎；每对手 ≥20 局。所有批量评测跑在 `kagsim` 上，
   官方 Python 引擎只做最终 parity 抽检（沿用 V76/V20 的 QA 惯例：
   打包后逐动作、逐奖励对拍）。
3. **口径**：逐对手胜率 + Wilson 区间；不看聚合平均金币；改动若使任一强对手
   胜率显著下降即否决，哪怕总胜场上升 [survey §3.3]。
4. **提交纪律**：一个 slot 放最强版本让它老化，另一 slot 只放真正的假设检验；
   同一 bot 不重复提交（对最终 BT 排名零收益 [survey §3.3]）。

## 8. 风险与 fallback

- **最大风险**：自搜的生产计划打不过千锤百炼的公开 tape（M2 预测不达标）。
  fallback 早已备好：**市场层（HoleLedger/OpponentLedger/WinLedger/Router）与
  生产层解耦**，可以整体嫁接到 `v1_adaptive_market` 的 replay 路线上——那条线
  的 README 里"下一步"恰好就是缺市场适应层。两条线在 M3 汇合是完全可接受的结局。
- **镜像高原**：若 V4 变强后行为趋同于 meta，胜负退化为时序掷硬币。缓解：M3 的
  race 层正是为镜像局设计的（先手率就是镜像胜率）；且账本驱动的行为随对手/商店
  变化，**tape 克隆者只能抄走某一局的轨迹，抄不走策略** [survey §3.6]——这本身
  就是对"24 小时被克隆"生态的结构性防御。
- **过拟合本地对手池**：匹配池每周漂移 [survey §3.3]。每周日用 solutions-survey
  巡视模式刷新 meta 代表，重跑 M2 的 fitness 评估。

## 9. 明确不做（及理由）

| 不做 | 理由 |
| --- | --- |
| 端到端 RL / BC | 社区天花板 80k vs 规则 190k，样本/信用分配/非传递性三重死结 [survey §3.4] |
| 在线深搜索（MCTS/beam） | 1s/步限制；meta 用 0.5ms 规则已够；离线搜索性价比高一个数量级 |
| 直接抄 replay tape | 已有 `v1_adaptive_market` 线在做，V4 的存在意义是可归因 + 反克隆 |
| 第四象限 / 16+ 畜群 / 纯牛群 | 社区与 V1 消融均为负结果 |
| 席位路由器 | kaito v27 的教训：内部分数更高但只修 1/3 真实败局，删比加好 [survey §2.2] |

`kagsim` 的三个 API 形态与分工：
- `run_many(jobs)`：动作流批量模式，5 万局/s——用于 PlanSearcher 中"计划 → 固定
  动作流"的粗筛与蒙特卡洛统计；
- `Game.observe/step`：live 逐步模式，0.26–0.32 s/局（瓶颈是 agent 的 Python）——
  用于对抗评测与账本类功能的开发调试；
- `kagsim_scenario.force_shops`：live + 钉商店——用于配对对照与 M6 场景重放。

注意事项：`done`/`step_count`/`reward` 在两个扩展间属性/方法形态不一致，harness
里统一用 `val(x) = x() if callable(x) else x` 兼容；`kagsim` 需要 CPython 3.12
（`.venv` 即是），别用 anaconda 3.13 跑评测。

26 维空间搜了 960 个个体也只收回 ~20k margin。下一代若要继续原创线，方向是
"日级静态规划 + 回合级执行"（每天 hour0 做一次当天全任务的整体排程），
或直接在 V4H 的账本-嫁接框架上加深（tape 内省以提高 race 触发率）。
