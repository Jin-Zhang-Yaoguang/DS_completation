## 小麦闭合了，却大量循环交易

```text
1989 实际采购 + 160 实际采收
  = 1834 实际销售 + 313 实际喂养 + 2 日终溢出 + 0 终局库存
```

至少 `1834 - 160 = 1674` 单位销售必然来自本局采购，占采购量84.163%。这是无需给同类商品分配身份的转售下界；不能把每一笔卖出都说成购买转卖。采购现金81071，销售收入75917，相差-5154；这个差额包含饲料用途及自产销售，不能直接称为交易亏损或策略利润。

小麦交易方向切换933次，其中425个 `decision_step` 同时有真实买入和真实卖出：

| decision_step | 真实买入 | 真实卖出 | 说明 |
|---:|---:|---:|---|
| 1 | 5，花134 | 0 | 首次买入 |
| 2 | 2，花56 | 0 | 再补库存 |
| 3 | 0 | 2，得56 | 开始卖出 |
| 4 | 2，花56 | 0 | 再次买入 |
| 5 | 1，花28 | 2，得56 | 首次同一步先卖后买 |
| 6 | 2，花56 | 1，得28 | 再次同一步卖买 |

源码能直接解释这种冲突：`market_orders` 的售出保留量以“今天还没喂的动物 + 半日余量 - 随身小麦”计算（R0 `main.py:525`）；补货目标却以“所有已拥有动物 + 半日余量”计算（`:557`），并且 `wheat_have` 读取原始库存，未统一反映计划中的卖出与当步单位动作。两者分母、时间点不同。`counts`还包含仓库和随身未放置动物，因此未投产牛也会扩大饲料采购目标。

这支持一个可证伪修复方向：将当步已确认可见的生产需求、单位动作后库存、计划净买卖与统一补货区间放进同一份库存账本。是否提高现金或胜率必须在新确认块验证，不能从425次循环就推断可挽回多少利润。

同类动物没有个体ID，逐只配对是FIFO诊断约定；不依赖这项约定的事实是：从day14至day24的每日起点，场上始终10牛，另有4牛在仓库或随身中，未形成生产能力。每只牛400，总计1600现金已经投入，四只在本局均没有产奶窗口。

R0能确认买到了动物，却没有确保新动物的放置任务、空建筑和地块在截止时间内完成。`make_tasks`先处理已有作物并 `continue`（R0 `main.py:327`），后面才生成动物预留格建筑（`:377`）；这是值得单独验证的建设调度瓶颈，不能仅凭采购数量正确就判扩张闭合。

## 校验和下一步

`validation.json` 确认：原动作带SHA正确、原候选没有被导入、引擎复合SHA一致、719动作完整、来源已保存的终局snapshot全部字段一致、双方现金与来源一致、逐商品实际交易/采收量与来源一致、每种商品库存守恒残差为0。来源snapshot是runner的终局摘要，未保存每步所有田块内部标记，这项校验不应称为逐帧源状态比对；原比赛另有完整官方/快引擎逐帧parity通过记录。动物与作物的照护、终局产物和丢弃来自完整规则内部事件，不是根据现金变化猜测。

后续机制比较应保持分母，并在两个席位分别报告：有产能的缺水损失、预先登记的退出、库存总量峰值与溢出、采购至投产在途量、同商品同一步双向交易、成熟残留。单局对PASS表现仅用于发现机制缺口。
