# R4 执行合约独立审查

范围：只读 `DESIGN.md`、冻结 `parent_r3.py` 与本地官方规则快照；不改候选、不跑比赛、不读取新 Replay 或 Blind。下列初审是规则约束与待验证条件，尚非实现缺陷。

## 设计核对

官方解释器先执行全部单位动作，再处理市场、作物衰减，最后在第 23 小时执行日更（`rules_snapshot/kaggriculture.py:894–963`）。因此 WATER / FEED 的当日最晚动作时点为 `day * 24 + 23`，收据可在下一日 `step + 1` 才确认。最后一天第 22 小时直接终止，不存在第 23 小时日终自动入仓。

1. **跨日收据先于 owner 清理。** 日更把 WATER / FEED 标志清零，同时将成功保活对应的连续未浇 / 未喂计数置零；雇工及各背包也清空（规则 769、805、843、860 行）。先按旧收据目标确认，再清理失效 owner；不能先因雇工消失或背包归零丢失合法完成记录。
2. **过期判定区分动作截止与收据截止。** 第 23 小时动作仍合法，收据次日才出现；先确认上一帧，再判断下一阶段还能否完成。不能用 `now > action_deadline` 提前否定尚未查看的收据。
3. **预期状态转移更新身份。** DIG→BUILD、PLANT→WATER、PLACE 动物都会合法改变目标 fingerprint。只在观测确认该动作后更新预期身份；外部替换对象必须取消，不能让旧合同继承新对象。
4. **不确定收据不当失败或成功。** 跨日 HARVEST 叠加自动入仓与日更产量；CARE 标志清零。无法消歧时应使用未确认原因，不计完成。WATER / FEED 跨日确认应要求上一帧对象一致、原标志为 False、已实际向目标格发动作、当前对象存活且相应连续计数为零。
5. **同格互斥包含所有活动合约。** travelling / resupplying / awaiting_receipt 也应占目标；新分配和抢占必须与已保留合约共用同一目标占用表。仓口搬运本身允许同格多工，但不能因此生成两个目标地块合约。
6. **供给预留只代表承诺。** 在途工人预约的仓内材料应在下一帧按真实库存重新核对；PICKUP 请求或路径命令不能算阶段完成。FEED 要有实际小麦，WATER / 已成熟 HARVEST 不应继承肥料前置条件。

## 最小机制场景

| 场景 | 必须观察的结果 |
|---|---|
| 第 23 小时主农 / 雇工分别 WATER、FEED | 下一日按目标保活计数确认；雇工合同随后终止，不错误累计 rejected |
| 第 23 小时 FEED 无粮，或 WATER 错误位置 | 不计完成，保留未确认 / 拒绝原因 |
| 第 22 小时身带肥料站在缺水作物，下一帧还能 WATER | 依次 FERTILIZE→WATER；第 23 小时同条件直接 WATER |
| 成熟作物需要浇水但肥料只在另一工人身上 | 可执行保活 / 成熟采收，不为取肥放弃最后可行窗口 |
| 两工人与一个空目标，已有移动合同后边际排名反转 | 目标只有一个 owner；无紧迫事件时持续原路径 |
| 一个仓内 WHEAT、两份待喂合同 | 同帧最多一个有效供给承诺；未取得粮者不虚报 FEED |
| DIG→BUILD、PLANT→WATER | 每阶段均等观测确认；合法变更身份不误取消，也不虚报链完成 |
| 目标被替换、动作被拒或 observation 跳步 | 取消 / 未确认并记录原因，不把发单或到达视为完成 |

### P2 剩余边界：owner 编号反向时仍有无谓抢占

冻结 `main.py:721–730` 按编号逐个检查活动合同，`other_urgent` 只排除已经放入 `occupied` 的目标。`test_microcases.py:162–169` 只覆盖 unit 0 先保活、unit 1 持 CARE 的方向。

对称条件为第 22 小时，unit 0 在 `(0,0)` 持有非紧迫 CARE，unit 1 在 `(1,0)` 持有 WATER；对 unit 0 而言，去 `(1,0)` 后 WATER 恰是最后窗口，但 unit 1 自己可以及时完成。检查 unit 0 时 `occupied` 仍为空，因此旧 CARE 合同被记为 `contract_urgent_preempted`。随后 unit 1 接受 WATER，unit 0 又可能重新接受原 CARE。动作可能不变，但稳定合同与抢占计账不成立；若同时存在另一个高排名目标，则具备无谓改派条件。

这是同一审查问题的反向处理顺序，已告知实现方，未修改已交付根代理冻结的源码。建议后续执行层修订先计算所有可继续履约 owner 的覆盖，再判断未覆盖的紧迫需求。未将该静态边界描述为已发生的完整比赛损失。
