2026-09-05。提案，无候选源码或新比赛。阶段 A 已交付；此文件不改变其已登记附件。

建议只替换 `d > obs.day` 的劳动可行性与对应雇工费用，当前日继续走冻结 R9 原劳动估计。资金前缀、净终值选择、任务分数和实际执行器保持原口径。未来日路线采用条件日初状态，只有完整覆盖该日全部竞争义务并经独立检查器通过，才可返回劳动证书；不能对未表示部分打折。

根最新拒绝诊断给出 29,563 次 labor 拒绝，其中 future_only 18,596（62.9%）、current_only 3,833、both 7,134；day9 六格链的 105 次全部为 current_only。**因此优先未来日是覆盖面的选择，不能把阶段 A 的六格证据直接归成这 18,596 次的共同原因。** 具体要改变哪些报价仍须逐条记录旧/新首个失败日。

## 1. 单一改变及不变的估值语义

旧门把资产日历的 `work[d]` 相加，再比较人数乘时槽；新门要求存在逐时槽合法服务路线，人数在 0..12 个 hand 中按固定顺序有限枚举，取第一个有证书者，费用仍按官方 FIB 序号逐单计算。

R9 `project_calendar` 的商品/饲料日历继续作为这次实验的条件目标；不同时改成熟收益、价格或 `net` / `net÷labor` 的定义。路线若无法完成日历中计入收益的产物交付，不可只删掉这项服务保留收入。若 route 得出的成熟状态/物量与原日历冲突，该日返回 `UNSUPPORTED_CALENDAR_CONFLICT`，保留原门并记录反例，不在本候选内顺手改收益预测。采用逐日fallback：某个启动日不支持时保留该日原labor与费用，其后完整照护日仍可尝试出证书，不把整个trial永久挡住。

新服务表示应保留三类相互独立的字段：原评分分母 `quote_labor_for_score`、旧日级工时 `legacy_work[d]`、证书的实际移动/服务/等待槽及雇工费用。仅用于劳动门的新路线数字不得悄悄覆盖供执行器使用的原 `crop_scores`。

## 2. 输入和输出接口

建议拆成三个可独立开发、独立审查的纯函数：

```python
compile_future_day(obs, state, accepted_projects, trial_project, day) -> DayProblem | Unsupported
schedule_day(problem, n_hands) -> Certificate | NoCertificate
check_day(problem, certificate) -> CheckResult
```

`DayProblem` 至少包括：

| 字段 | 内容与来源 |
|---|---|
| `clock` | 日、有效 h0..23；day29 仅 h0..22 |
| `start_farm` | 所有已在田资产的种类、出生、存量产品、dry/unfed、care bonus、fertilized/寿命字段；不能只给一个工时数字 |
| `start_stores` | 各商品仓内物量、种子、仓容100、已预留不可出售/不可挪用的数量；每一份有來源lot |
| `start_workers` | 未来日农夫固定 `(4,4)`、空背包；hands为空、hires_today=0 |
| `services` | 唯一 `service_id=(asset_id,day,stage,batch)`、位置、earliest/deadline、前置阶段、消耗和产物、对应原日历项 |
| `market_conditions` | 当日外购麦数量与完整费用、可用时刻、雇工费用、销售保留量、最多10单；费用传给原前缀重查 |
| `assumptions` | 日初状态的来源、当前日仍待完成的启动、未来补粮/价/销售条件，逐项列明 |
| `coverage` | 全部存量、已有承诺和trial的资产/阶段id；缺任何竞争义务则不出完整证书 |

`Certificate` 输出逐 `step/unit` 动作、逐市场命令、资源流事件、服务与交付lot、末状态、雇工出生位置/首可动时刻、各工人MOVE/服务/PASS计数、未覆盖项和problem hash。`scheduled` 与真实完成仍分别记；不能由许可证书直接生成 `actual_completed`。

## 3. 最小条件日初，不假称未来已知

当前日使用原劳动门，未证明今天的执行结果。未来第一个日初可由原资产日历及当前未完成启动产生条件状态，必须列出如“项目 P 在今天完成 PLACE”的假设。实际在途不能直接改成实在田资产，来源类型保留为 `conditional_activation`。

随后在连续证书日期内按前一份末资产/背包/仓存及官方日终刷新派生日初；不能每天重新使用同一粒自有麦。植物 dry、生产轮次/存量上限、动物 care bonus 的先消耗后追加顺序、寿命衰退均须与官方一致。若上一日是未支持的fallback日，下一日只能从原生命周期/及时照护假设构造日初，并显式记录 `conditional_bridge_from_legacy_day`，不能伪称它由证书证明。日历要求某日产物但模型冲突时，该日回原门，原收益模型保持不变。

首版可把未来补粮和可出售商品的成交作为**公开列出的条件**，不实现整套对手/商店预测策略。粮食使用原 `funding_feed_schedule` 的 `buys_by_day/stock_by_day` 生成条件料账，并保留来源与消费lot；收入价格继续来自 R9 的已有模型。日内路线核物量、仓容、订单槽和费用供原前缀重查。连续证书日期的物量承接已列出的当日条件；跨fallback桥接明确重新依赖模型，不能免费增加未列的物料。

随机新杂草只影响空格启动；已到位存量上的服务不需预测随机空格。需要未来随机空格保持空白、未来解锁地或尚无完整启动链时，该启动日返回 `UNSUPPORTED_STARTUP`，走原 R9 门；其后仍要生成条件照护义务。此保守fallback须逐日报原因，并按报价和资金量报告覆盖率，不能只报少数通过样本。

## 4. 全部义务怎样转为服务

按资产/出生去重，再按原日历和实际已完成flag生成未完成阶段。已在途中且未确认的合约占有真实材料；与同一项目的许可合并，不重复计 PLANT/首水或 BUILD/PLACE。

- 作物：每次应水的 WATER；日历计入产物的 HARVEST；终结性采收后不得再列同一资产的 WATER/FERTILIZE。原模型依赖既有肥效则保留其有效期；不能凭未来免费施肥补出模型产量。
- 动物：每日缺失 FEED 及相同模型依赖的 CARE；产物 HARVEST；肥料 COLLECT_FERTILIZER。奶和肥可共享访问，但必须是两次合法服务动作。
- 粮食：每次 PICKUP 从真实条件仓存扣减，取量采用 R9 原最多4麦的执行能力；每次FEED消耗已由该工人携带的1麦，预约不算实际拥有。
- 交付：采收/收肥先进入该工人背包；回明确仓口后按品种执行 PLACE。不同商品不能合并成一次PLACE，也不能把远处背包当仓内可卖。
- 未完成启动：若阶段跨入要替换的未来日，必须显式包含取动物/运输/PLACE或DIG/BUILD/播种/首水等全部阶段；首版没有完整链时该启动日为UNSUPPORTED并保留原labor，后续天从原生命周期的有条件激活状态继续；不能把未支持启动称为已出证书。

官方无背包总件数上限，不能添加虚构载重约束。反过来，R9现有动作能力只允许按品种PLACE，本轮证书也不能用新的批量DROP效率。日终自动转仓是真实状态刷新，仍计容量和可能丢弃；它不替代日历要求的当日可售交付。day29没有h23自动帮忙变现。

## 5. 固定未来雇工与市场顺序

采用根建议的确定性协议，避免凭项目选择出生口：

1. h0农夫固定PASS。市场最多9条HIRE加1条BUY WHEAT；每单雇工按当时实际占用从四仓口中选最少者、固定顺序tie-break。新手h1可动，买麦h1才可PICKUP。
2. 需要第10..12名hand时在h1市场雇，h2才可动。出生口按h1已执行单位动作后的实际占用重算；不能提前指定。
3. 同一frame顺序是农夫、hands依index执行，再市场。checker逐单位处理共享库存，禁止多个PICKUP重复领走同一粒粮；市场BUY不能支撑本帧先发生的FEED。
4. 每帧最多10条市场命令。条件SELL只用该市场时刻实际已在仓且不被保留的商品；PLACE能先于同帧SELL释放，但SELL不会替更早发生的PLACE腾空。未能卖出的数量继续占仓。
5. 同期HIRE/BUY的费用完整进入原cash prefix；当前真实采购仍受观察cash限制，不借未成交SELL。未来日费用先扣的R9前缀规则不变。仅市场物量可行不等于价格和未来现金保证兑现。

固定h0 PASS及9+1槽是**证书假设**，冻结R9实际市场/执行器未被改成该协议。必须报告实际HIRE、材料到位和行动偏离；不能称“R9必定沿此证书”。如果这类差异系统性使新增许可落空，后续需要单独执行承诺设计，本轮不能假装劳动表示已解决兑现。

## 6. 排程算法：确定性构造，不做一般最优规划

先固定人数和h0/h1招聘事件。将同一地块可连续执行的服务视为一个带内部顺序的访问段，但逐操作保留service id。确定性选择“最早截止、插入后最早完成、最短新增移动、service id、unit id”，不加收益权重或参数搜索。

每次插入都在副本中重演受影响工人的后续动作及共享资源账；需要麦时加具体仓口PICKUP段，货物应交付时加具体返仓和按品种PLACE段。必须给其它工人同期动作和末尾交付留合法槽；不能只加距离后忽略已承诺时槽。放不下全部服务则返回NO_CERTIFICATE。

服务允许共享移动：一条访问路径可以在多格连续WATER，或在同格FEED/CARE/HARVEST/COLLECT后一次返仓交付两品种。但不宣称找到最短路线。人数从服务操作槽给出的保守下界起有限枚举到12；下界只省去不可能的人数，不参与放行。

## 7. 开销、缓存、trial回滚

R9每帧可能上百quote，不能每次不加区别重排30日。输入服务池不可变，按`day/problem_hash/n_hands`缓存。hash必须包含完整资产状态、服务阶段、存料、保留量、招聘/价格费用条件和依赖假设，不能只用资产个数。

trial只重算新增项目影响的日期及其状态/库存改变后的后续依赖日。若某日末状态与baseline完全相同，可复用后续缓存；否则不可因为该日没有新增WATER就跳过。与价格重价相关的费用变更依旧触发原资金前缀重查。

拒绝trial必须回滚服务池、物量lot、日初/日末状态、缓存写入作用域、人数/费用和现金信用；保存baseline hash核对。调度失败不能回退成“已打折工时的通过”；fallback只允许走**完全未变的原R9劳动门**并标来源。

先在已打开少量真实报价上记录调用数、缓存命中、最坏运行时间与unsupported率，再决定能否进入singlefile。没有实测性能前不承诺整局1秒限制可过。

## 8. 分块实现与验证责任建议

我可以负责两块：服务/条件日初compiler与不可变trial/cache包装；确定性访问段生成器。生成器不导入候选或父agent。根可并行实现独立 `check_day` 及官方局部控制，r4_review只读核需求完整性、官方时钟和独立性。
